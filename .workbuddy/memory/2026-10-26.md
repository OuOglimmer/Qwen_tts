## 槽位「查看历史声线」（13:40）

`attach_voice` 也校验 `status='active'`、全代码没有 `replaced → active` 的回写。

### 追加：一次删除把整个后端打挂了（14:47）

用户点历史声线弹窗的「删除」并确认 → `DELETE /api/library/voices/{id}` 500，
随后 uvicorn 进程直接消失（任务 RNmmh4 退出码 1）。原因不是业务逻辑：

- `voice_assets.delete_voice_asset` 先调 `backup_snapshot`（这是对的，删前先备份）；
- `backup_snapshot` 末尾清理第 31+ 个旧快照 `shutil.rmtree(old_snapshot, ignore_errors=True)`；
- 我这个后端是从 Agent shell 启的，`PYTHONPATH` 里带着 WorkBuddy 的 `sitecustomize` 垫片，
  它拦截 rmtree，发现目标 `backups/pre-delete-project-DEMO-20261020-175821` 有 499 个文件
  （阈值 50）→ 抛 `SystemExit(1)`；`ignore_errors=True` 抓不到 `BaseException`，
  异常一路穿到 ASGI，整个进程被带走。

结论与处置：

- **数据无损**：备份是在事务之前做的，崩溃时删除还没执行，`voices` 仍 60 行（原样）；
  崩溃前生成的 `backups/pre-delete-voice-哪吒-20261026-144601` 里 app.db + 该声线目录都在。
- 重启时改成 `PYTHONPATH= ... -m studio.api`，垫片不再加载（`sitecustomize not in sys.modules`，
  `shutil.rmtree.__module__ == 'shutil'`）。重发同一条 DELETE → 200 `{"deleted":"哪吒"}`，
  历史 11 → 10，服务存活，快照数回到 30。
- 这条只影响"从 Agent shell 启动的后端"，用户双击 `start_studio.cmd` 不会有这个垫片。

### 追加：重新固化前的确认（15:40）

需求：已固化的槽位再固化新声线时，要提示"当前槽位已固化声线，是否重新固化"。

关键事实（决定实现方式）：`select_candidate` 只把 `status` 写回 `selected`，**不清 `voice_id`**。
所以「fixed 槽位 → 重新选定候选」之后，就是 `status='selected' && voice_id IS NOT NULL` ——
这就是"这次固化会覆盖一个正在生效的声线"的唯一准确信号，不需要新接口或新字段。

改动只有 `VoiceWorkbench.fix()` 开头一段：筛出 `status==='selected' && voice_id` 的槽位，
命中就 `await confirm({ danger: true })`，点名这些槽位，说明旧声线留成 replaced 历史版本、
已生成的成品不跟着变（仍标「已换版」）。点取消直接 return，不会进 `setFixing`。

反面：**解冻后再固化不弹确认**，这是对的 —— `reopen_fixed_request` 已经把旧资产置 replaced 了，
此时没有再退役任何在用的东西。
