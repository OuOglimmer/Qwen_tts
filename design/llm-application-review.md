# 大模型应用视角评估：Qwen-TTS Voiceover Studio

> 评估对象：`studio/`（FastAPI 后端，5392 行）+ `frontend/`（Next.js 14）  
> 评估维度：提示词工程、上下文/ICL、RAG 与检索、模型配置、可复现性、可观测性  
> 结论依据：全部来自代码实测核验，非文档转述；关键处标注文件与行号

---

## 0. 先定性：它是「生成模型应用」，不是「LLM 应用」

这一点必须先说清，否则后面所有对比都会错位。

核验结果：

| 常见 LLM 应用组件            | 本项目实况                                       |         |       |                                        |
| ---------------------- | ------------------------------------------- | ------- | ----- | -------------------------------------- |
| 文本大模型 / Chat API       | **无**。依赖只有 `torch` + `qwen-tts`，无任何 LLM SDK |         |       |                                        |
| 对话 / 多轮 / Agent 编排     | **无**。没有任何 system/user 分层，没有工具调用循环          |         |       |                                        |
| Prompt 模板引擎（Jinja 等）   | **无**。`instruct` 就是一段人类写的自然语言字符串            |         |       |                                        |
| Embedding / 向量库 / 语义检索 | **无**。全仓 \`embedding                        | retriev | faiss | vector` 零命中（`x_vector_only\` 是 TTS 术语） |
| 文档切分 / chunking        | **无**。批量台词是「一行一文件」，切分责任交给用户                 |         |       |                                        |

它真正的形态是：**一个 1.7B 自回归 TTS 模型的工程化控制台**（声线设计 → 候选筛选 → 固化 → 批量合成 → 导出）。模型输出是音频码流，不是 token 文本。

所以本文的比较不是「套模板打分」，而是分三类看：

- **同构的**（LLM 应用怎么做，这里也怎么做，甚至做得更好）→ 提示词工程、上下文缓存、输出守门
- **结构性缺失的**（LLM 应用必备，这里天然不需要）→ 多轮编排、工具调用
- **缺失但需求真实的**（LLM 应用有，这里没有且应该补）→ 检索增强、prompt 版本化、推理可观测性

一句话判断：**这个项目的提示词工程水平明显高于它的检索能力，而它的模型配置工程水平又高于它的提示词闭环能力。**

## 1. 提示词工程

这是全项目投入最重、也最成体系的一块。它没有停在「给个输入框让用户写」，而是做了一套**受控词表 + 结构化模板 + 填槽交互**。

### 1.1 提示词的形态与流向

单一 instruct，无分层：

```
voice_requests.prompt  (人类自然语言描述)
        │
        ├─→ POST /api/tools/design ──→ tools.design_sample(prompt)
        │                                   └→ models.design(text, language, prompt, seed)
        │                                          └→ model.generate_voice_design(instruct=prompt, max_new_tokens=512)
        │
        └─→ POST /api/voices/design-archive ──→ archive_designed_voice()
                                                   └→ 只存 voices.prompt（不再进模型）
```

关键事实：**`voices.prompt` 只写不读**。全仓两处 INSERT 写它，**零处**在合成路径读取它（`grep` 已核验）。固化之后，合成只吃 `prompt.safetensors` 里的 speaker embedding + ref_code。

这是本项目最重要的架构特征，第 4 节会展开。

### 1.2 六段式结构规范

`frontend/lib/promptPresets.ts:23`

```
[性别年龄]，[音色质感]，[语速节奏]，[语调起伏]，[情绪态度]，标准普通话，[适用场景]。
```

- 固定 6 个维度、固定顺序、全角逗号连接、句号收尾
- `scene` 段前自动补「标准普通话」（`composePrompt`，`:130-138`）
- 空选择返回空串，不会拼出半截提示词

这个设计的价值：把开放式生成任务收敛成**有序槽位填充**。TTS 的 instruct 对「形容词堆叠」很敏感，顺序和粒度不稳定会直接导致音色漂移；固定六段等于给模型一个稳定的语义骨架。

### 1.3 受控词表

6 维共 42 个候选词（`promptPresets.ts:26-57`）：

| 维度   | 选项数 | 覆盖范围                                           |
| ---- | --- | ---------------------------------------------- |
| 性别年龄 | 11  | 6 岁～45 岁，童声/青年/中年分档                            |
| 音色质感 | 10  | 柔和温暖 / 清亮甜美 / 低沉醇厚 / 低沉有磁性 …                   |
| 语速节奏 | 4   | 平缓 / 适中 / 稍快 / 干脆利落                            |
| 语调起伏 | 5   | 平稳 / 轻柔自然 / 自然起伏 / 抑扬顿挫 / 上扬有活力                |
| 情绪态度 | 7   | 温柔亲切 / 沉稳专业 / 热情洋溢 / 俏皮可爱 / 冷静客观 / 坚定有力 / 慵懒随性 |
| 适用场景 | 8   | 纪录片 / 广告 / 客服 / 有声书 / 少儿 / 新闻 / 短视频 / 宣传片      |

### 1.4 模板库与「成对」设计

11 个场景模板（`promptPresets.ts:60-127`），每个是 `{prompt, audition}` **成对**结构。

这个成对设计容易被忽略但很关键：候选生成时用 `audition` 作为合成文本，所以**同一轮 4~8 个候选读的是同一句话**。用户 A/B 对比时听到的唯一变量就是声线本身，而不是「这段广告词 vs 那段旁白」带来的错觉。

换成 LLM 应用的语言：这是**控制变量法的评测集设计**。很多 prompt 工程的 A/B 失败就失败在示例文本同时变了。

### 1.5 交互层：不静默覆盖

`PromptAssist.tsx` + `promptAssist.ts`：

1. 模板一键填入 → 若当前提示词已被用户编辑过，弹「覆盖当前提示词？」确认（`promptAssist.ts:22-31`）
2. 维度组装器弹窗 → 实时预览拼接结果 → 「应用到提示词」
3. 配套试听文本**只在未填写时**自动补，绝不覆盖已写内容（`:33-35`）

`safePrompt` 这类细节（区分「空串」与「用户手动改过但恰好等于模板」）在大模型应用里很少见，属于认真做过用户体验的痕迹。

### 1.6 问题：词表与模板是两套真相源

这是我目测发现、并逐条比对过的真实缺陷。

「按维度组装」走词表，模板走硬编码字符串，两者**没有任何生成关系**。逐段比对 11 个模板 × 5 个主要维度（55 段）：

| 维度   | 模板用词不在词表内  | 典型例子                                                          |
| ---- | ---------- | ------------------------------------------------------------- |
| 性别年龄 | **7 / 11** | 模板「约25岁/23岁/28岁/33岁/38岁/42岁/8岁」，词表只有 6/9/20/24/26/32/35/42/45 |
| 语调起伏 | **7 / 11** | 「语调沉稳有分量」「语调平稳有质感」「语调活泼跳跃」「语调节奏感强」——词表里都没有                    |
| 情绪态度 | **6 / 11** | 「语气沉稳自信」「语气耐心亲切」「语气沉稳从容」「语气天真好奇」「语气亲切有活力」                     |
| 音色质感 | 4 / 11     | 「音色醇厚温暖」「音色清脆甜美」「音色明亮清晰」「音色明快自然」                              |
| 语速节奏 | 1 / 11     | kidsStory「语速稍慢」（词表只有平缓/适中/稍快）                                 |

合计约 **45% 的分段用词游离在词表之外**。

后果不是功能错误，而是**词表的权威性失效**：用户以为「词表 = 系统支持的全部表达」，实际模板里有近一半表达是词表外的，而模型对这两种写法的响应没有记录、没有评测。所谓「受控」，只控住了组装器，没控住模板。

修法（低成本）：模板不要写字符串，改成喂 `composePrompt()` 的 selection 对象，由词表生成 prompt 文本。这样加词表自动扩展模板，也不可能漂移。

### 1.7 问题：prompt 没有版本，回溯链断裂

`_prepare_candidate_request`（`voice_workflow.py:285-292`）在重新生成候选时直接 `UPDATE voice_requests SET prompt=?`，旧值**原地覆盖**。

所以：

- `candidates` 表有 `round`、有 `seed`、有 `wav_path` —— **候选是版本化的**
- `voice_requests.prompt` 是单值 —— **提示词不是版本化的**

结果是「这条被选中的候选，是第 3 版提示词生成的，但第 3 版长什么样已经不知道了」。想复现「为什么这版好听」只能靠人脑。

对 LLM 应用来说这是硬伤：prompt 迭代没有 diff，就无法归因。建议新增 `prompt_versions(request_id, version, prompt, audition_text, language, created_at)`，candidates 外键指向 version。

### 1.8 问题：无校验、无负面提示

- `DesignPayload.prompt` 只有 `min_length=1`（`api.py:184`）。10000 字的描述照样能提交，模型只会静默截断或忽略
- 没有长度上限、没有维度完整性检查（缺「语速」也能生成）
- 没有负面表达（TTS instruct 一般也不推荐「不要 XX」，但可以用「避免」类措辞；这点属于可讨论而非硬伤）
- 前端模板库是**编译期常量**，运营想加一个「有声剧旁白」模板必须发版

## 2. 上下文与 ICL：其实是本项目最「LLM 原生」的一环

很多人看 TTS 会漏掉这块，但它和 LLM 的 in-context learning 是同构的，而且这里做成了双模式。

### 2.1 两种克隆模式的语义差异

`ModelManager.clone()`（`model_manager.py:178-227`）+ `create_prompt()`

| 模式                         | 传给模型的上下文                                      | LLM 类比                        | 质量           |
| -------------------------- | --------------------------------------------- | ----------------------------- | ------------ |
| `x_vector_only=True`       | **只有** speaker embedding（x-vector）            | 只给 system prompt 定人设，不给示例     | 低，但无需转写      |
| `x_vector_only=False`（ICL） | `ref_code`（音频 codec token 序列）**+** `ref_text` | 给一组 `(示例输入, 示例输出)` few-shot 对 | 高，要求参考音频逐字转写 |

`archive_uploaded_voice` 里的强制校验正好印证这个类比：

```python
if not x_vector_only and not ref_text.strip():
    raise ValueError("高质量克隆模式必须填写参考音频对应文字")
```

这就是 few-shot 里「示例必须包含标注」的硬约束。设计上把「质量 vs 标注成本」的取舍显式交给用户，而不是偷偷用低质量模式，这个判断是对的。

### 2.2 `prompt.safetensors`：本项目最聪明的一处成本优化

`save_prompt` / `load_prompt`（`model_manager.py:243-269`）

固化声线时把 `ref_spk_embedding` + `ref_code` + `ref_text` + 模式标记 一次性落盘成 safetensors；之后每次合成直接 `load_prompt` 反序列化，**不再重新编码参考音频**。

这在 LLM 应用里的等价物是 **embedding 缓存 / KV cache 预热**：把「每次请求都要付的编码成本」前置到「资产创建时付一次」。

对本项目的意义尤其大——批量合成 200 行台词时，少掉的不是 1 次而是 200 次参考音频编码。这是一次性设计换来的长期吞吐收益。

### 2.3 缺陷：safetensors 不记录模型身份

`save_prompt` 写入的 metadata 只有 `ref_text` / `x_vector_only_mode` / `icl_mode`（`:251-255`），**没有模型名、没有版本、没有 embedding 维度**。

而 `.env` 明确允许换模型：

```
QWEN_TTS_CLONE_MODEL_PATH=D:/ouyang/model/voice_clone_0.6b
# 12GB 显存如需更高克隆质量，可下载 1.7B Base 后把下面一行改为 ...voice_clone_1.7b
```

换到 1.7B 后：

- 若 embedding 维度不同 → 加载报错（还算好，至少炸了）
- 若维度相同但语义空间不同 → **静默变声**，所有历史声线资产听起来都不是原来那把声音，且无任何告警

这是资产与模型耦合关系缺失导致的可复现性漏洞。修法：metadata 加 `model_id` / `model_rev` / `embedding_dim`，加载时不匹配就拒绝并提示重新固化。

## 3. RAG：基础设施为零，但需求是真的

### 3.1 核验结论

| 检索相关能力                   | 实况                                                                 |
| ------------------------ | ------------------------------------------------------------------ |
| 文本 embedding             | 无                                                                  |
| 向量库（faiss/chroma/qdrant） | 无，依赖表里没有                                                           |
| 语义/模糊搜索                  | 无。列表接口全是 `ORDER BY created_at DESC` 直出                             |
| 精确检索                     | 有：`voices.name` UNIQUE 约束、`audio_hash` MD5 去重、`project_voices` 关系表 |

`archive_uploaded_voice` 的去重是这样做的（`voice_assets.py:121-137`）：

```python
audio_hash = _file_md5(reference_wav)
duplicate = self.db.fetch_one("... WHERE v.reference_hash=? AND v.status='active'")
if duplicate: raise ValueError("声线库已有相同参考音频的声线「X」...")
```

MD5 是**字节级精确匹配**。同一段音频转个码、裁掉 0.2 秒静音、换个采样率，hash 全变，去重直接失效。这是「有检索动作，但没有检索能力」的典型状态。

### 3.2 为什么缺席是合理的

TTS 的 `instruct` 是**控制信号**，不是知识查询。它不需要「从外部语料里捞出相关段落塞进上下文」——模型参数里已经有发音能力，用户要的是「让输出符合这段描述」。

拿 RAG 框架硬套会得到一个错误结论（「缺少 RAG，应该补」）。准确的说法是：**这里没有「知识不足」的问题，所以不需要知识检索；但有「资产太多找不到」的问题，所以需要资产检索。**

这是两种不同的检索，不能混。

### 3.3 三个真实存在的「检索增强」落点

按 ROI 排序：

**落点一：声线库语义检索（最该做，成本最低）**

现状：`library_voices()` 直接全表返回 active 资产，前端平铺。40 个声线时还能靠肉眼扫，200 个就是灾难。

可以做：把 `voices.prompt` + `ref_text` + `tags` 拼成文本做 embedding，实现「我想要一个讲睡前故事的温柔女声」→ top-5 现有声线。**不需要调外部 API**——本地 `bge-small-zh` 之类 100MB 级模型足够，或直接用模型自带的文本编码器。

存储也不必上向量库：SQLite + 内存 cosine（几百条数据暴力扫 <1ms），或用 `sqlite-vec` 扩展。投入产出比极高。

**落点二：优秀 prompt 的 few-shot 检索（这才是真 RAG）**

现在 11 个模板是**编译期常量**，等于「静止的 few-shot 池」。

真 RAG 应该是：把历史上**被用户采纳**的 `(prompt → 选中候选的音频特征/prompt 本身)` 沉淀成经验库，新需求来时检索 top-3 相似历史 prompt 作为参考，甚至作为 instruct 的前缀示例。

前置条件是 1.7 节说的 prompt 版本化 + 采纳率回流。没有版本化，这条链根本起不来。

**落点三：参考音频近似去重**

MD5 升级为「音频指纹」：重采样到 16k 单声道 → 截取中间 5 秒 → MFCC/chromaprint 特征 → 余弦相似度 >0.95 视为重复。这样「同一段录音换了编码再传」也能拦住。

### 3.4 明确不建议

**不要引入向量库做文档问答。** 本项目没有长文档知识库，没有政策/手册/FAQ，`voices` 表 12 列里没有一列是需要「读懂」的文本。上 RAG 框架只会增加一层无用的复杂度。

## 4. 模型配置

这是全项目工程化程度最高的部分，也是最不灵活的部分。

### 4.1 实际部署配置

来自 `.env`（已 gitignore）+ `config.py:52-60`：

| 角色        | 路径                  | 规模       | 说明                                    |
| --------- | ------------------- | -------- | ------------------------------------- |
| 声线设计（文→音） | `voice_design_1.7b` | 1.7B     | `generate_voice_design(instruct=...)` |
| 克隆（文→音）   | `voice_clone_0.6b`  | **0.6B** | 注意不是文档示例里的 1.7B                       |
| 硬件        | RTX 3060 12GB       | —        | 文档里写「约 8GB 显存」，实际 12GB                |

`.env` 注释说得清楚：「clone 使用 0.6B：加载快、显存余量大」。这是一个**刻意的性能取舍**：用更小的 base 模型换更快的加载和更大的并发余量。

但这个取舍只在 `.env` 里，代码默认值和 `.env.example` 都是 1.7B（`config.py:57-59`）。**新人 clone 仓库直接跑，拿到的是和作者不同的模型**。这是配置管理缺口，建议把实际部署值写进 `.env.example` 并加注释说明取舍理由。

### 4.2 加载参数（全硬编码）

`model_manager.py:145-150`

```python
Qwen3TTSModel.from_pretrained(
    str(path),
    device_map="cuda:0",      # 单卡写死，无 CPU fallback
    dtype=torch.bfloat16,     # 精度写死
    attn_implementation=None, # 未启用 flash-attn / sdpa
)
```

这四项都无法通过配置改。对个人工具是合理简化，对团队复用是硬门槛。`attn_implementation=None` 意味着放弃了一个可能有 20~30% 提速的空间（3060 支持 sdpa）。

### 4.3 生成参数

| 参数                   | design          | clone                           |
| -------------------- | --------------- | ------------------------------- |
| `max_new_tokens`     | **512 固定**      | `96 + 字数×6`，clamp `[128, 2048]` |
| `non_streaming_mode` | 未设（模型默认）        | `True`                          |
| `seed`               | 有 `manual_seed` | **无**                           |
| 重试                   | 无               | 最多 5 次                          |
| 输出校验                 | 无               | 有（三重）                           |

`max_new_tokens=512` 的换算（12.5 frame/s）：

```
512 / 12.5 = 40.96 秒
```

**设计路径的文字上限硬顶在 41 秒左右，且没有任何兜底校验。** 超长试听文本会被静默截断，用户听到的是半句话，且系统不报错、不重试、不提示。

而 clone 路径反而做了精细估算（`model_manager.py:110-121`）：

```python
estimated = 96 + units * 6      # 12 码率 token/秒，留出停顿余量
return max(128, min(2048, estimated))
```

这个 6 倍系数是「每个字大约占多少 token」的经验值，配合 `[128, 2048]` 上下界，既防短句跑飞几分钟，也防长句被 81.8 秒硬顶截断。**注释里明确记录了这个坑的踩坑史**（「former 1024-token/81.8-second cap」），这是好工程习惯。

问题是：**两条路径的严谨度不对称**。design 是主力生成路径（候选生成、快速试听都走它），却守门最薄。这是我认为最该优先补的技术债。

### 4.4 采样参数：一个都没传，全靠库默认

全仓 `temperature|top_p|top_k|repetition_penalty|do_sample` **零命中**——不是设成了某个值，是**一个参数都没传**。

而上游库的默认值是这样的（`qwen_tts/inference/qwen3_tts_model.py:320-328` 的 `_merge_generate_kwargs`）：

```python
do_sample=True
top_k=50
top_p=1.0
temperature=0.9        # ← 偏热
repetition_penalty=1.05
```

也就是说：**本项目实际跑在 temperature=0.9 的采样模式上，但代码里看不见这个数字。** 这是最典型的「隐式配置」——行为由上游默认值决定，本地无可读、无可调、无记录。

对 TTS 的 codec 语言模型而言，0.9 是个偏热的档位：它给韵律和音色带来表现力，也是「同一句话两次生成语速不一样」「偶尔跑调或吞字」的主要来源。项目花了大力气做输出守门（4.6 节的三重校验 + 5 次重试），本质上是在**用重试兜住一个温度偏高的采样器**。这层因果关系，代码里没有一处写明。

建议：

- 在 `design()` / `clone()` 里**显式传参**，哪怕值和默认相同。目的的让「用了什么参数」在代码里可读
- 只暴露两个旋钮给用户：`seed`（锁定重放，见 4.5）和 `temperature`（低=稳定，高=有表现力但可能失真）
- 把 `(temperature, top_k, seed, model_id)` 落进产物元数据。否则调完参后，老音频和新音频分不清是「参数变了」还是「seed 变了」

零成本、不影响存量音频，是性价比最高的一处改动。

### 4.5 可复现性：三条路径三种结果

| 路径                                            | seed 来源                | 是否可复现                                                      |
| --------------------------------------------- | ---------------------- | ---------------------------------------------------------- |
| 候选生成 `voice_workflow._generate_one_candidate` | `SystemRandom.randint` | **可**（seed 落 `candidates.seed`，同硬件同版本下 `manual_seed` 重放一致） |
| 独立试听 `tools.design_sample`                    | `SystemRandom.randint` | **不可**（seed 未落任何地方，用完即丢）                                   |
| 批量合成 `clone()`                                | **无 seed 控制**          | **不可**（`clone()` 里没有 `manual_seed` 调用，只有 `design()` 有）     |


第二、三条是真实缺口：

- 独立试听不可复现 → 用户听到一段很满意的声音，点「入库」后**不能靠重新生成找回**。这个坑已经被规避了（`design_id` 回传同一段音频），但属于「用架构绕过问题」而非「解决问题」。一旦临时目录被清理（`temp/standalone/voicedesign/` 无清理机制但也不保证永存），这段声音就永久丢失
- 批量合成不可复现 → 改了错别字重新生成，**整条音轨的韵律都变了**。批量有 `version` 机制（保留最近 3 版），但那是「保留旧版」，不是「同版重放」

修法很小：`clone()` 里加 `torch.manual_seed(seed)`，`tools.design_sample` 把 seed 一并返回并落进产物元数据。

### 4.6 输出守门：全项目质量最硬的一环

`_audio_is_usable`（`:65-75`）+ `_clone_audio_is_usable`（`:78-107`）+ 5 次重试（`:216-227`）

三重判据：

1. **信号健全性**：`numel > 0`、`isfinite().all()`、`peak >= 1e-3`、`rms >= 1e-3`
   → 拦掉空音频、NaN、近静音
2. **截断检测**：`duration >= max_new_tokens/12.5 - 0.35` 判失败
   → 输出贴着 token 预算 = 跑飞或截断，不是正常结束（留 0.35s 余量防止边界误判）
3. **语速合理性**（仅中文）：`字数/8 <= duration <= 字数/1.5 + 2`
   → 上下界都卡，慢到 8 秒一个字、快到 1.5 秒一个字都算异常

这是标准的 **generate → validate → retry** 模式，在 LLM 应用里对应 structured output 的 schema 校验 + 重试。设计得很扎实，尤其是「贴着 token 预算就判失败」这条——很多人会漏。

但有两个缺口：

- **只保 clone，design 裸奔**。`design()` 完全没有校验（对比 `clone()` 的 5 次重试）。而 design 是候选生成的主力路径，一条静音候选会直接进候选栏让用户听
- **重试是同参数 resample，不做诊断也不降级**。如果失败根因是 `max_new_tokens` 估小了，5 次重试必然全失败（每次都截断），最后抛「模型连续生成了过短、近静音或未正常结束的音频」。用户看到这句话完全无法定位问题。且没有记录每次尝试的 `duration/peak/rms`，事后无法归因

建议：重试前记录一次指标快照到日志；连续 2 次因「贴顶截断」失败时，自动把 `max_new_tokens` 上调 1.5 倍再试（降级策略而非纯重试）。

### 4.7 并发与生命周期

三重锁，层次清晰：

| 锁 | 位置 | 保护对象 |
|---|---|---|
| `threading.RLock` | `ModelManager._lock` | 所有推理调用串行（GPU 一次只能跑一个） |
| `msvcrt` 字节范围锁 | `CrossProcessGpuLock` / `gpu.lock` | 跨进程互斥（第二个进程直接拒绝启动模型） |
| `threading.Lock` | `VoiceWorkflowService._fix_lock` | 固化流程的读-改-写原子性（防双击产生重复资产） |

`CrossProcessGpuLock` 的设计值得一提：用 `msvcrt.locking(fd, LK_NBLCK, 1)` 锁文件首字节，非阻塞、进程退出自动释放（`atexit` 兜底）。比 PID 文件方案干净得多，不需要处理「僵尸 PID」。

切换模型时 `unload()` 会 `del model` + `gc.collect()` + `torch.cuda.empty_cache()`（`:154-163`）。这是显存受限场景的标准动作。

代价是：**design 和 clone 不能同时常驻**，每次切换都要重新从磁盘加载 1.7B/0.6B。在一个「设计声线 → 固化 → 批量合成」的完整流程里，这个切换会发生多次。如果加载耗时 10~20 秒，用户感受就是「每隔一会儿卡一下」。

这是 12GB 显存的现实约束，不是设计缺陷。但可以在 UI 上做预期管理（系统状态页显示「当前已加载：design / 加载中…」），现在 `status()` 已经返回 `model` 字段（`:271-278`），前端有数据可用。

## 5. 架构级判断

### 5.1 「提示词即资产，但固化后即冻结」

这是我认为最值得说的一条。

正常的 prompt 工程闭环是：

```
写 prompt → 生成 → 评估 → 改 prompt → 再生成 → ...
```

本项目固化后的实际形态是：

```
写 prompt → 生成 → 选中 → 固化(prompt → safetensors) → 之后只吃 safetensors
                                                    ↑
                                          prompt 从此只写不读
```

`voices.prompt` 只在两处 INSERT 出现，**合成路径零读取**。改声线库里的描述文字，声音一点不变。

后果：
- prompt 从「可迭代的接口」降级成「人类可读的溯源标签」
- 用户以为能「微调描述」，实际只能「重新设计一条新声线」（换 seed 换声音，等于从头来）
- 声线的**可编辑性彻底丢失**

这对一个「提示词工程做得这么认真」的项目来说是矛盾的：最精细的那套六段式规范，只在设计阶段用一次，之后永久失效。

改进方向（这是我认为最有价值的一条设计建议）：

```sql
-- voices 增加三列
ALTER TABLE voices ADD COLUMN design_seed INTEGER;
ALTER TABLE voices ADD COLUMN design_model TEXT;
ALTER TABLE voices ADD COLUMN design_version INTEGER;  -- 描述的第几版
```

有了 `(prompt, seed, model)` 三元组，就能：
1. **同描述 + 同 seed 重放**：确认「固化下来的确实是当时听到的那把声音」
2. **同描述 + 换 seed**：生成「同一个角色的不同演绎」，这才是配音场景真实需要的（同一角色，不同情绪、不同语速）
3. **改描述 + 同 seed**：做 prompt 的 A/B，因为 seed 固定，变量只有描述

第 3 条是真正的 prompt 工程闭环——**把 seed 当随机种子固定住，prompt 变成唯一自变量**。现在的设计里 seed 和 prompt 一起变，永远无法归因。

### 5.2 两条入库路径的语义一致性

`design_id` 回传机制（`api.py:1025-1031` + `_resolve_design_audio:1040-1053`）值得单独点出：

```python
# design_id 由后端生成并用作文件名：前端点「入库」时原样回传，
# 后端据此定位**用户刚试听的这一段**，不用重新生成（重跑会换一个 seed）。
```

在「生成不可复现」的前提下，这是唯一正确的做法。而且安全上做了双校验（uuid 形态正则 + `relative_to(root)`），防目录穿越。

同时注意 `_resolve_design_audio` 优先取 `.wav` 而非 `.mp3`：

```python
# 优先取中间 wav：固化要拿它原样做 reference.wav，mp3 只是试听件。
```

避免了一次无谓的有损解码。这种细节说明作者对音频链路是有实际体感的。

### 5.3 没有 chunking，长文本责任外推

- design：40.96 秒硬顶（512 token）
- clone：动态预算，超顶判失败重试，但仍不切块
- batch：`pasted_text.splitlines()`，一行一文件

整个系统假设「一行台词 = 一次生成」。文本超长时不会自动分句、不会跨段拼接、不会在断点处对齐韵律。

对 LLM 应用来说这是 chunking 缺失；对配音场景来说这可能是**有意为之**——自动切分会让断点落在语义不该断的地方，专业配音宁可人工分行。

但缺少的是**提示**：用户在试听文本框里贴了 300 字，系统应该告诉他「这段约 2 分钟，超出单次生成上限，建议按句分行」。现在什么都不说，直接给一段被截断的音频。

### 5.4 可观测性：有业务流水，无推理指标

有的：
- `activity_log`：关键业务动作（固化、选择、丢弃候选…）
- `jobs`：任务级计数（total / succeeded / failed / 耗时）
- `batch-regeneration.log`：批量重生成的 RotatingFileHandler

缺的：
- 推理侧指标：每次生成的**耗时、RTF（realtime factor）、token 数、失败原因分类**
- 守门失败的原因分布：是静音、截断，还是语速异常？
- 模型加载耗时、切换次数

LLM 应用里这些属于基础可观测性（latency / token usage / error rate）。TTS 的等价物是 RTF 和守门失败率。有了这些数据，「design 该不该加守门」这种判断就不用猜了。

## 6. 评分与优先级

| 维度 | 现状 | 评分 | 主要问题 |
|---|---|---|---|
| 提示词工程 | 六段式 + 42 词表 + 11 模板 + 覆盖确认 | **B+** | 词表与模板漂移 ~45%；无版本；无校验 |
| 上下文 / ICL | ICL 与 x-vector 双模式，取舍显式化 | **A-** | safetensors 不记模型身份 |
| 提示词闭环 | 固化后 prompt 只写不读 | **C** | 声线不可编辑，无法 A/B |
| 检索增强（RAG） | 零基础设施，只有 MD5 精确去重 | **D** | 声线库无语义检索；音频无近似去重 |
| 模型配置 | 三重锁 + 输出守门 + 动态 token 预算 | **B** | design 无守门；clone 无 seed；采样参数全隐式（跑在 temp=0.9） |
| 可复现性 | 候选路径可复现，其余不可 | **C+** | 试听 seed 丢弃；批量生成无 seed |
| 可观测性 | 业务流水完整，推理指标为空 | **C** | 无 RTF / 失败归因 |

### 优先做的前三件

**P0 — design 路径补齐守门 + 显式传采样参数 + clone 补 seed**
改动量最小、收益最直接。`design()` 复用 `_clone_audio_is_usable` 的时长校验思路（按字数估时长区间）；`design()` / `clone()` 把 `temperature/top_k/top_p/repetition_penalty` **显式写出来**（值可先等于库默认，目的是可读可调）；`clone()` 加 `torch.manual_seed`，`design_sample` 返回并持久化 seed。半天工作量，一次堵住三个真实痛点：静音候选进候选栏、批量重生成全变调、调参不可追溯。

**P1 — prompt 版本化 + `(prompt, seed, model)` 三元组入库**
这是解锁「声线可编辑」和「prompt 可 A/B」的前置条件。有了它，1.7 节的回溯断裂和 5.1 节的编辑性丢失一起解决。

**P2 — 声线库语义检索**
`voices.prompt + ref_text + tags` 做 embedding，本地小模型，SQLite 暴力扫即可。纯增量，不动现有表结构。声线过百之后这是刚需。

### 明确不要做

- 不要引入 LangChain / LlamaIndex 之类的编排框架：本项目没有多步链、没有工具调用、没有 stream 拼装需求，框架只会增加一层黑盒
- 不要上向量数据库：几百条数据，`sqlite-vec` 或内存暴力扫完全够
- 不要做「文档问答」型 RAG：没有知识文档，没有这个需求

## 附：一句话总结

这个项目的提示词工程做到了「把开放创作收敛成结构化填槽」，模型配置做到了「三重锁 + 三重守门 + 动态预算」，这两块都超出一般个人项目的水平。

它真正的短板不在「模型用得对不对」，而在**「用完就冻结」**：prompt 固化后失效、seed 用完就丢、声线一旦生成就不可编辑。缺的不是能力，是**闭环**——把「哪次生成、用什么描述、什么种子、效果如何」串成可回溯的数据链。

而这恰好也是 RAG 与 prompt 工程在这个项目里唯一的真实交集：不是在合成时检索知识，而是在**设计时检索历史经验**。
